# Геркулес Клуб — система обліку клієнтів

**Технічне завдання для агента розробки.**
Виконуй послідовно за етапами M0→M6. Не переходь до наступного етапу, поки не виконані критерії приймання поточного.

---

## 0. Контекст

Міні фітнес-студія у Києві (Харківське шосе, 172Б). Один зал, одна стійка рецепції, один адміністратор у зміну. ФОП. Клуб орієнтований на ветеранів: відновлення, реабілітація, самостійні тренування.

Це **не** система записів на заняття. Клієнт приходить коли хоче, підносить клубну картку до сканера, тренується, йде. Головне питання, на яке система відповідає за півсекунди: **пускати чи ні**.

### Три потоки людей у залі

| Потік | Гроші | Абонемент | Облік |
|---|---|---|---|
| Клієнт клубу | через рахунок ФОП | так, перевіряється | повний |
| Гість орендаря | повз клуб, напряму тренеру | немає | тільки факт присутності |
| Тренер-орендар | платить оренду клубу | немає | присутність |

Гроші гостя орендаря **ніколи** не потрапляють у виторг клубу. Це вимога банківського комплаєнсу, а не побажання.

## 1. Архітектура

```
GitHub repo (публічний, тільки код)
        │
        ├── GitHub Pages ──► https://<user>.github.io/herkules-desk/
        │                          │
        │                    Chrome на міні-ПК (встановлений як PWA)
        │                          │
        │                    ┌─────┴─────┐
        │                    │           │
        │              IndexedDB    File System Access API
        │            (основна база)      │
        │                                ▼
        │                    G:\Мій диск\Геркулес\База\Бекапи\
        │                                │
        └────────────────────► Google Drive for Desktop ──► хмара
```

### Чому саме так

- **GitHub Pages** дає `https://`, а без secure context не працює File System Access API. Заодно — автооновлення без походу до міні-ПК.
- **Service Worker** кешує все: інтернет зникає разом зі світлом, застосунок працює далі.
- **IndexedDB** — основна база, локальна, миттєва.
- **File System Access API** пише бекап прямо в синхронізовану папку Google Диска. Ніякого Google API, OAuth і токенів, що протухають.
- **Жодного бекенду.** Один зал, один адміністратор — сервер тут лише додаткова точка відмови.

### Стек

- Vanilla JS, ES-модулі, **без збірки** — відкрив файл і читаєш
- Без фреймворків, без npm-залежностей у рантаймі
- CSS — власний, змінні в `:root`
- Ідентифікатори в коді англійською, UI і коментарі українською

### Заборонено

- localStorage/sessionStorage для бізнес-даних (ліміт 5 МБ, синхронний, втрачається при очищенні кешу) — тільки IndexedDB
- Будь-яка відправка даних клієнтів на зовнішні сервіси
- CDN у рантаймі — все локально в репозиторії

## 2. Модель даних

IndexedDB, база `herkules`, версія схеми в константі.

```js
Client {
  id: string            // "HC0001" — він же штрих-код
  type: 'member' | 'guest' | 'trainer'
  name: string
  phone: string
  birthday: string      // ISO
  isVeteran: boolean
  medicalNotes: string  // травми, обмеження — чутливі дані
  consentAt: string     // дата підпису згоди на обробку ПД
  hostTrainerId: string // тільки для type='guest' — до кого прийшов
  createdAt: string
  archivedAt: string|null
}

Subscription {          // активний абонемент, вкладений у Client
  tariffId: string
  title: string
  startDate: string
  endDate: string
  visitsTotal: number|null   // null = безліміт
  visitsLeft: number|null
  freeze: {
    active: boolean
    since: string|null
    reason: 'service' | 'injury' | 'other' | null
    daysUsed: number
  }
}

Visit {
  id: string
  clientId: string
  checkIn: number       // timestamp
  checkOut: number|null
  autoClosed: boolean   // закрито системою о 23:00, а не сканом
  subscriptionTitle: string
  clientType: string    // копія на момент візиту
}

Payment {
  id: string
  clientId: string
  date: string
  amount: number
  method: 'cash' | 'card'
  item: string
  tariffId: string|null
  fiscalReceiptNo: string|null   // номер чека Checkbox, вводиться вручну
  note: string
}

Tariff {
  id, title, visits: number|null, days: number, price: number, forVeterans: boolean
}
```

**Історичні записи не редагуються.** `Visit` і `Payment` пишуться один раз. Виправлення — сторнуючим записом з посиланням на оригінал, не правкою.

## 3. Бізнес-правила

### 3.1 Рішення про допуск

Функція `evaluateAccess(client) → {allow, level, reason}`. Перевірки в цьому порядку, перша спрацювала — та й повертається:

| # | Умова | Результат |
|---|---|---|
| 1 | `type` = 'guest' або 'trainer' | ✅ ДОЗВОЛЕНО, абонемент не перевіряється |
| 2 | немає абонемента | ⛔ «Немає абонемента» |
| 3 | `freeze.active` | ⛔ «Заморожено з {дата}» |
| 4 | сьогодні < `startDate` | ⛔ «Почнеться {дата}» |
| 5 | сьогодні > `endDate` | ⛔ «Закінчився {дата}» |
| 6 | `visitsLeft` ≤ 0 | ⛔ «Візити вичерпано» |
| 7 | залишилось ≤3 дні або ≤2 візити | ⚠️ ДОЗВОЛЕНО + попередження |
| 8 | інакше | ✅ ДОЗВОЛЕНО |

### 3.2 Списання візиту

Візит списується **на вході**, не на виході. Причина: люди йдуть не відмічаючись, візит загубиться.

Кнопка «Скасувати вхід» доступна 5 хвилин після сканування: видаляє `Visit`, повертає візит на баланс. Після 5 хвилин — тільки через режим адміністратора з логуванням.

### 3.3 Абонемент спливає під час тренування

Клієнт зайшов вранці, `endDate` = сьогодні. Тренування завершує нормально, вихід фіксується без помилок. Перевірка терміну — тільки на вході.

### 3.4 Заморозка

- `reason: 'service'` (на службі) — **без ліміту днів**, це ключова ветеранська умова
- `reason: 'injury' | 'other'` — ліміт `MAX_FREEZE_DAYS` днів на абонемент, за замовчуванням 30
- При розморожуванні `endDate` подовжується на кількість заморожених днів
- Заморожений абонемент не пускає в зал

### 3.5 Автозакриття змін

О `CLOSE_TIME` (за замовчуванням `23:00`) всі відкриті `Visit` закриваються з `autoClosed: true`. Тривалість не рахується — ставиться `null`.

**Мета:** список «хто зараз у залі» має бути правдивим. При тривозі адміністратор дивиться на цей екран, і вчорашні привиди в ньому неприпустимі.

Автозакриті візити підсвічуються в журналі окремо — це показник дисципліни сканування, не норма.

### 3.6 Межа доби у звітах

Доба у звітах = `[OPEN_TIME, CLOSE_TIME]`, не `[00:00, 23:59]`. Візит, що почався о 22:40, належить сьогоднішньому дню повністю.

Винести в `config.js` окремим блоком нагорі, з коментарем «ЗАПОВНИТИ ПЕРЕД ЗАПУСКОМ»:

```js
export const CONFIG = {
  OPEN_TIME:  '08:00',   // ⚠️ уточнити
  CLOSE_TIME: '23:00',   // ⚠️ уточнити — визначає автозакриття і межу доби
  MAX_FREEZE_DAYS: 30,   // для причин, крім служби
  UNDO_WINDOW_MIN: 5,
  BACKUP_INTERVAL_MIN: 120,
  BACKUP_KEEP: 30,
  CARD_PREFIX: 'HC',
  CLUB_NAME: 'Геркулес Клуб',
  CLUB_ADDRESS: 'Київ, Харківське шосе 172Б'
};
```

## 5. Екрани

### 5.1 Стійка (головний, за замовчуванням)

Поле сканування у фокусі **завжди**. Клік будь-де на порожньому місці повертає фокус. Сканер працює як клавіатура: код + Enter.

Один скан = перемикач. Клієнта немає в залі → вхід. Є в залі → вихід.

Вердикт займає верхню третину екрана і читається з двох метрів:
- **зелений** — проходь
- **жовтий** — пусти, але скажи, що абонемент спливає
- **червоний** — стоп, причина великим текстом, кнопка «Продати абонемент» поруч

Нижче — плитка «У залі зараз»: імʼя, тип клієнта, час входу, скільки вже в залі.

Невідомий код → пропозиція створити клієнта з цим номером картки (щоб можна було роздати заздалегідь надруковані картки).

### 5.2 Клієнти

Таблиця з пошуком (імʼя / телефон / номер картки) і фільтрами: активні, спливають, прострочені, ветерани, гості орендаря, зараз у залі.

Картка клієнта: анкета, поточний абонемент, історія візитів, історія оплат, друк клубної картки.

**Медичні нотатки показуються першими у картці.** Тренер має побачити «грижа L4–L5, без осьового навантаження» до початку заняття, а не знайти це через три кліки.

### 5.3 Продажі

Список оплат за період, сума, експорт CSV. Поле «номер фіскального чека» — заповнюється вручну після проведення в Checkbox.

### 5.4 Журнал

Усі візити з фільтрами за датою і клієнтом. Автозакриті — окремою позначкою. Експорт CSV.

### 5.5 Налаштування

Тарифи, папка бекапів, стан останнього бекапу, ручне відновлення з файлу.

## 6. Бекап

### Механіка

1. При першому запуску — `showDirectoryPicker()`, адміністратор вказує папку бекапів на диску G:
2. Handle зберігається в IndexedDB, дозвіл перевидається через `requestPermission()` при кожному старті
3. Запис відбувається: кожні `BACKUP_INTERVAL_MIN` хвилин, при закритті зміни, при закритті вкладки
4. Формат імені: `herkules-YYYY-MM-DD-HHMM.json`
5. Зберігаються останні `BACKUP_KEEP` файлів, старіші видаляються

**Датовані знімки, не один перезаписуваний файл.** Якщо база зіпсується, зіпсований стан не має затерти всі попередні.

### Індикатор

У шапці постійно: «Копія: 14:22 ✓» або «Копія: 3 дні тому ⚠️» червоним. Проблема має бути видна одразу, а не через місяць.

Якщо доступ до папки втрачено — банер із кнопкою «Вказати папку заново», при цьому робота не блокується.

### Відновлення

Кнопка «Відновити з файлу» → вибір JSON → показ що всередині (скільки клієнтів, візитів, дата) → підтвердження → заміна бази.

## 7. Штрих-коди

- **Code 39** — читається будь-яким USB-сканером без налаштувань, підтримує літери
- Генерація SVG власною функцією, без зовнішніх бібліотек
- Номер картки: `HC0001` і далі послідовно
- Друк клубної картки 86×54 мм: назва клубу, імʼя, штрих-код, номер під ним, адреса
- Дубль коду в QR для Telegram — картку забувають, телефон ні

Якщо сканер не читає Code 39 — перемкнути на EAN-8 через конфіг. Закласти цю можливість одразу.

## 8. Персональні дані

Медичні нотатки — це дані про стан здоровʼя, окрема категорія за Законом «Про захист персональних даних».

- Поле `consentAt` обовʼязкове до заповнення перед першим візитом
- Папка бекапів на Google Диску **не шериться** ні з ким і не лежить у спільному диску
- Експорт CSV з медичними нотатками — окремою кнопкою з попередженням
- Видалення клієнта — з підтвердженням і повним видаленням історії

## 9. Етапи

### M0 — Репозиторій

- `herkules-desk`, публічний, ліцензія MIT
- README: що це, як запустити локально, як розгорнути на Pages
- `.gitignore`: `*.json` з даними, `.DS_Store`, `node_modules`
- GitHub Pages з гілки `main`, папка `/`
- **Критерій:** порожня сторінка відкривається за https-адресою

### M1 — Ядро даних

- IndexedDB: схема, міграції, CRUD
- `evaluateAccess()` з покриттям усіх 8 гілок таблиці 3.1
- Unit-тести правил доступу (простий тест-раннер, без залежностей)
- **Критерій:** тести проходять, усі гілки покриті

### M2 — Стійка

- Сканування, вхід/вихід, вердикт, «у залі зараз», скасування входу
- **Критерій:** сканування картки USB-сканером дає вердикт за <300 мс

### M3 — Клієнти, абонементи, оплати

- Реєстр, картка клієнта, продаж, заморозка/розморозка, тарифи
- Друк клубної картки зі штрих-кодом
- **Критерій:** повний цикл — створив клієнта, продав абонемент, пустив у зал, візит списався

### M4 — Бекап

- File System Access, автозапис, ротація, індикатор, відновлення
- **Критерій:** файл зʼявляється в папці G: і видно в Google Диску з телефону

### M5 — Автономність

- Service Worker, офлайн-режим, PWA-маніфест, іконки
- Автозакриття змін о `CLOSE_TIME`
- **Критерій:** вимкнути інтернет — застосунок працює повністю

### M6 — Розгортання на міні-ПК

Окремий файл `DEPLOY.md` з покроковою інструкцією:

1. Google Drive for Desktop під акаунтом клубу, поява диска G:
2. Папки: `Геркулес → База → Бекапи`
3. Chrome → відкрити Pages-адресу → «Встановити застосунок»
4. Ярлик PWA в автозавантаження Windows, друге вікно на другому моніторі
5. Перший запуск: вказати папку бекапів, перевірити появу файлу
6. **Тест відновлення на іншому компʼютері** — обовʼязково до відкриття
7. Щотижнева перевірка дати останнього файлу з телефону

## 10. Сценарії приймання

Прогнати вручну перед передачею:

1. Новий клієнт → продаж пакета 8 візитів → 8 входів → девʼятий заблоковано
2. Прострочений абонемент → червоний вердикт із датою закінчення
3. Заморозка на 10 днів → розморозка → `endDate` подовжено рівно на 10
4. Заморозка з причиною «служба» на 90 днів → ліміт не спрацьовує
5. Гість орендаря → пускається без абонемента → у виторзі не зʼявляється
6. Вхід о 22:50 → о 23:00 автозакриття → у звіті належить сьогоднішньому дню
7. Скасування входу через 2 хв → візит повернуто на баланс
8. Вимкнути інтернет → сканування працює → увімкнути → бекап пішов
9. Забрати доступ до папки → банер, робота не заблокована
10. Відновлення з учорашнього файлу на чистому браузері

## 11. Поза скоупом

Не робити, навіть якщо здається корисним:

- **Фіскалізацію.** Checkbox — окремий контур, чек пробивається в його інтерфейсі. У системі тільки поле для номера чека.
- **Онлайн-запис і розклад груп.** Зал самостійних тренувань, записуватись нема на що.
- **Товари, склад, сертифікати, ваучери.** Клуб продає тільки послуги — це рішення власника з причин банківського комплаєнсу, а не спрощення.
- **Мобільний застосунок, особистий кабінет, розсилки.** Пізніше, якщо система доживе до потреби.
- **Мультилокаційність, ролі, права доступу.** Один зал, один адміністратор.

## 12. Правила роботи агента

- Комміти атомарні, повідомлення українською, префікси `feat:`, `fix:`, `docs:`
- Гілка на етап: `m1-core`, `m2-desk` — мердж у `main` після виконання критерію
- Після кожного етапу — короткий звіт: що зроблено, що не вийшло, які рішення прийняв самостійно
- Не додавай залежності без узгодження
- Не змінюй бізнес-правила з розділу 3 — якщо правило виглядає нелогічним, запитай, а не виправляй
- Коментуй тільки неочевидне: чому саме так, а не що робить код
